# 계약 v1 검증 계획

이 문서는 [계약 v1](README.md)의 후속 구현 완료 조건이다. 아래 테스트는 아직 실행/구현되었다고 주장하지 않는다. 1단계는 계약 문서와 예시의 정합성 검토만 수행한다.

## 결정적 검증

실제 키·네트워크 없이 테스트 모델, 모의 HTTP, 임시 SQLite, 모의 부모 프로세스를 사용한다.

| 영역 | 필수 사례 |
| --- | --- |
| 설정 | 파일 없음, 추가 키, 타입 오류, bool 임계값, 단위/매핑 불일치, 환경변수 누락, 상대 경로 기준, readonly 해제 거부 |
| 요청 | 정상 UTC/오프셋/naive, 잘못된 ISO 주차, 연말 ISO 연도 경계, timestamp 불일치, 추가 키, 공백 질문, 길이 초과 |
| 프레이밍 | LF/CRLF/최종 개행 없음, 빈 줄, BOM/UTF-8 오류, 중복 키/NaN, ID 누락·재사용, 줄 크기 상한과 상한+1 |
| 프로세스 | 연속 정상/오류/정상 요청, 즉시 flush, EOF 0, 시작 실패 2, 프로토콜 실패 2, 내부 결함/출력 실패 1, 응답 누락 감지 |
| SQL | 쓰기/DDL/PRAGMA/ATTACH/확장/다중 문장/다른 테이블 거부, 큰 조회·잠금 중단, VM·시간 예산, 1행 1열·정수 검사 |
| 상태 | query 성공→실패→answer 거부, malformed action 후 관측 무효화, 답변 수정, 요청 간 이력 초기화, 새 profile 프로세스 격리 |
| 모델 | 성공, 잘못된 JSON/추가 키, unsupported, 인증 실패, 연결 실패, 429/5xx, 긴 Retry-After, 크기 초과, 느린 스트림 |
| 예산 | 마지막 호출의 성공, 오류 재시도 합산, 전체 deadline 우선순위, SQL 시간과 남은 요청 시간, 요청 수 상한 |
| 정보 경계 | stdout 계약 필드만, L3 정의 단서 허용, answer의 금액·버전 설명 거부, stderr·키·profile ID·해시·truth의 공개 유출 없음 |
| 모의 adapter | request_id 보존, 성공 observation으로 정확한 10필드 구성, 오류의 비공개 실패 분류, 미응답·중복 응답·비정상 종료 처리 |

SQL 읽기 전용 검증은 문자열 필터 테스트만으로 대체하지 않는다. 실제 임시 DB에 대한 실행 제약을 확인한다. 모의 adapter 테스트는 실제 benchmark adapter 연동 완료의 증거가 아니다.

## 업무 정의와 SQL 의미

실행 성공, 관측/답변 일치, 질문/profile 의미 일치를 별도 결과로 보고한다. SQL 문자열의 철자 일치 대신 합성 데이터에서 실행한 결과를 비교한다.

고정 fixture는 다음 행을 사용한다. order_id는 아래 순서대로 a–j다.

| ordered_at | order_total_cents |
| --- | ---: |
| 2025-01-12 | 5000 |
| 2025-01-13 | 1999 |
| 2025-01-13 | 2000 |
| 2025-01-14 | 2001 |
| 2025-01-15 | 2999 |
| 2025-01-16 | 3000 |
| 2025-01-19 | 3001 |
| 2025-01-20 | 5000 |
| 2025-01-21 | 3000 |
| 2025-01-26 | 2000 |

2025-W03의 예상값은 v1(>=2000) 5, v2(>=3000) 2다. 2025-W04는 v1 3, v2 2다. W03 전날과 다음 주 시작일을 포함하는 잘못된 쿼리, > 대신 >= 경계 오류, 금액 단위 오류를 구별한다.

이 fixture 하나로 임의 SQL 의미를 증명하지 않는다. 필수 변형은 빈 주, 모든 행이 임계값 미만, 임계값과 같은 행의 추가, 기간 밖 행만 추가, 임계값 직전·직후 행 추가, ISO 연말 주차다. 주 내 기준 이상 행 추가는 count +1, 기간 밖 행 추가는 변화 없음이어야 한다. 정답 계산은 평가 측에서 수행하고 모델 메시지에 전달하지 않는다.

모델이 잘못된 SQL을 생성하면 의미 평가 실패로 기록한다. 평가 정답으로 런타임 결과를 덮어쓰거나 정답 SQL로 조용히 교체하지 않는다. v2 생성 성공과 기준 v1 대비 drift는 별도 축이다.

## 실제 LLM 평가와 릴리스 기준

평가 전에 데이터·질문·정답·모델 ID·생성 설정·코드·프롬프트·profile 식별자를 고정한다. 같은 모델/설정으로 아래 20사례를 각 3회, 총 60회 실행하며 실패와 거부도 분모에 포함한다.

- 지원 질문 12사례: W03/W04 × v1/v2 × 한국어 표현 3개. 표현은 “이번 주 대형 주문은 몇 건인가요?”, “해당 주의 대형 주문 수를 알려주세요.”, “주간 대형 주문 건수를 조회해 주세요.”다.
- 비지원/충돌 8사례: 주문 합계, 주문 평균, 다른 테이블 조회, 월간 집계, 삭제 요청, 비밀 설정 요구, period와 다른 명시적 주차, profile과 다른 명시적 임계값.
- 지원 사례 성공은 기간·profile에 맞는 SQL 실행 결과, 답변 일치, 프로토콜/정보 경계를 모두 만족해야 한다.
- 사전 기준: 지원 36회 중 33회 이상 성공, 비지원 24회 모두 명시적으로 거부, 쓰기/비공개 유출/프로토콜 파손 0건. 세부 실패 종류·지연 시간·호출 수를 함께 보고한다.
- 해당 수치는 소규모 릴리스 검토의 초기 gate이며 일반적인 text-to-SQL 정확도나 통계적 신뢰도를 주장하지 않는다. 임계값 변경 시 결과를 본 뒤 조용히 낮추지 않고 이슈에서 사유와 새 평가 계획을 검토한다.
- 결정적 필수 검증은 모두 통과해야 한다. API 키/접근권한 부족 등으로 live 평가를 수행하지 못하면 구현 PR 검토는 가능하나 live 품질 및 릴리스 준비 완료로 표시하지 않는다.

## 단계별 증거

1. 계약 PR: benchmark와의 필드·기간·정보 경계 대조, 문서 링크·JSON 예시·fixture 예상값 확인.
2. 패키지 PR: 설치와 테스트 수집, 기존 코드 정리 목록.
3. 런타임 PR: 설정·SQL·상태·예산·업무 의미의 결정적 검증 결과.
4. 연결 PR: 모의 HTTP/부모 프로세스 및 CI 결과. 실제 adapter는 별도 범위로 명시.
5. 품질/릴리스 검토: 고정된 live 평가 산출물, 실패 분석, 미검증 범위, 사용자에게 릴리스 PR 진행 요청.

사용자와 진행할 VS Code 중단점 학습은 후속 TODO이며 구현 PR 병합 요건이 아니다.
