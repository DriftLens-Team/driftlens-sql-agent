# SemAlign v2 검증 기록

이슈 [#18](https://github.com/DriftLens-Team/driftlens-sql-agent/issues/18)에 사용자의 순차 구현 승인 근거를 기록했다. 개발 변경은 dev 대상 검토용이며 main 릴리스·병합 승인을 포함하지 않는다. v1 기본값·설정·응답은 보존하고 v2를 명시적으로 선택한다. 설치 패키지 버전은 기존 개발 버전을 유지한다.

## 검증 범위

- 키 없는 단위 테스트: 설정·기간·scalar·null·반올림, 허용 SQL·읽기 전용 예산, 요청 간 상태 격리, v1 회귀.
- 독립 손계산 DB: 세전/세후 평균, 혼합 품목 포함/제외, 활성 고객 임계값, 전체 이력 신규 고객, 전주 대비 비율과 세율.
- 실제 companion CLI: benchmark의 독립 8주 자료 56건과 로컬 driftlens-data 364건을 fake provider로 생성해 전부 검수 통과.
- 개선 전 소규모 실제 Upstage `solar-pro4-260806` 실행: 7개 지표를 한 번씩 호출해 응답 7건, benchmark 검수 통과 3건·탈락 4건. 통과율 3/7은 해당 표본에만 해당하며 이후 개선 효과를 나타내지 않는다.

실제 모델에서 평균 주문액·신규 고객은 시간대 접미사가 없는 DB 값과 `...Z` 경계 문자열 비교가 달랐다. 성장률에는 전주 이력 완전성 조건이 빠졌고, 세율은 정수 나눗셈과 세금 0의 null 처리 문제가 있었다. 실행값과 답변은 맞았지만 올바른 업무 정의를 구현하지 못한 사례다. 원본 응답을 보존했고 추가 호출로 교체하지 않았다. 이 7건은 첫 주 표본이며 drift 양성 평가나 전체 364건 실제 모델 검증을 뜻하지 않는다.

benchmark의 검수 정책은 두 가지다. `structural`은 검수기와 탐지기가 SQL 의미 추출 코드를 공유하므로 통과 관측의 높은 탐지 점수만으로 독립 정확도를 주장할 수 없다. `behavioral`은 별도 Python 참조 계산과 반례 DB의 실행 결과를 기준으로 생성 관측을 검수하며, 탐지기의 SQL 의미 추출 성공 여부를 검수 통과 조건으로 삼지 않는다. 이때 `query_correct_for_used_definition=null`은 SQL 의미를 판정하지 않았다는 뜻이고, 주요 판정은 `behavioral_agreement`에 기록한다. 유한한 DB 사례의 결과 일치는 임의의 데이터에 대한 SQL 정당성 증명이 아니다. 상세 집계와 재현 명령은 benchmark의 `docs/semalign-verification.md`에 기록한다.

## 재검토 후 개선

모델이 올바른 주간 요청을 받아도 SQL에 Z를 다시 붙이는 경로를 확인했다. 호스트가 현재 요청에서 계산한 날짜 매개변수를 SQLite에 바인딩하고, 실제 확장 SQL을 관측으로 남기도록 개선했다. Z/offset timestamp literal과 SQLite ROUND는 거부하고 기존 예산 안에서 수정 피드백을 전달한다. 주석 속 문자열은 검사 대상에서 제외한다. 값이나 SQL을 기대 정답으로 교체하지 않는다.

독립 경계 검토에서 전주 시작 정각 timestamp를 짧은 날짜 문자열과 비교하면 이력이 불완전하다고 잘못 판단하는 공통 오류도 발견했다. 이력 완전성 경계는 전체 timestamp로 비교하고 주간 집계 범위는 날짜 경계를 유지한다. 프롬프트에 실수 비율, 0인 분자, 빈 주 SUM, 전체 이력 신규 고객의 규칙을 명시했다.

추가 회귀는 자정 주문 포함·실행 SQL 확장, 잘못된 날짜/ROUND 거절 후 수정, 전주 시작 정각과 1초 뒤의 차이, 빈 현재 주, 세금 0, 2.5 cents의 한 번만 수행하는 ties-to-even 반올림을 확인한다. 실제 모델의 개선 효과는 후속 실행 결과로 별도 보고한다.

## 전체 실제 모델 실행

2026-10-28 개선된 agent로 `solar-pro4-260806`의 7개 지표·52주, 364개 요청을 실행했다. benchmark의 behavioral 검수 결과는 통과 270건(74.2%), 탈락 93건, SQL 실행 실패 1건이다. 음료 주문·활성 고객·평균 주문액·평균 세율은 각 52/52건, 신규 고객은 51/52건, 음식 주문은 11/52건 통과했고 성장률은 통과 관측이 없다.

음식 주문의 품목 제외 조건, 신규 고객의 중복 집계, 성장률의 전주 완전성 조건에서 실제 모델 오류를 확인했다. 원본 응답은 재호출로 교체하지 않았다. 검수기의 진단 표시 수정 후 저장 응답 363건을 모델 호출 없이 재검사했으며 통과·탈락 판정은 유지됐다. 전체 결과와 분모·판정률은 benchmark의 `docs/semalign-review-results.md`에 기록한다. 초기 7건 실행과는 표본·검수 기준이 다르므로 직접적인 개선율로 비교하지 않는다.

## 실행 명령

2026-10-28 개선 후 로컬 결과: 단위 테스트 59개 통과, wheel 빌드 성공. wheel의 prompt 2개와 Python 파일 컴파일을 확인했고 별도 설치 경로에서 capabilities가 agent/v2와 7개 개념을 반환했다.

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests/unit -p "test_*.py" -v
.venv/Scripts/python.exe -m build --wheel
```

새 dataclass 검증 훅, CLI 진입점, 모델 교체 메서드는 호출 인터페이스에 필요하다. parse·값·답변 검증은 실행 경계와 서로 다른 검증 사례에서 재사용한다. benchmark 내부 모듈은 import하지 않는다. SQL 권한 제한은 유지하지만 OS 프로세스 격리는 제공하지 않는다.

## 2026-10-29 날짜 리터럴 수정 검증

pstack 검토에서 SQLite가 큰따옴표 날짜를 문자열로 실행하면 시간대 접미사 검사와 수정 피드백이 생략되는 오류를 확인했다. 주 시작 자정의 100센트 주문과 다음 날 300센트 주문을 사용한 재현에서 작은따옴표는 수정 후 평균 200센트를 반환했지만, 큰따옴표는 수정 없이 300센트를 반환했다.

날짜 형태의 큰따옴표 토큰을 검사 SQL에서만 대괄호 식별자로 바꾸고, 같은 SQLite 연결에서 `EXPLAIN` 준비로 이름을 해석한다. 실제 식별자는 유지되고, 문자열로 처리되던 값은 `sql_error` 수정 피드백을 받는다. 실제 실행과 관측에는 원래 SQL을 사용한다. Python 3.11에서 없는 DQS 설정이나 SQLite opcode 형식에 의존하지 않는다. 미사용 CTE 내부 값처럼 SQLite가 이름을 해석하지 않는 부분은 전체 텍스트 금지 대상이 아니며, 이 제한은 계약에 명시했다.

새 사례를 먼저 추가하자 기존 코드의 6개 subtest가 실패했다. 수정 후 변경하지 않은 원래 재현에서 두 따옴표 모두 수정 1회 후 200센트를 반환했다. 날짜 형태의 정상 열·별칭·CTE 이름, 주석, 시간대 없는 timestamp, 호스트 날짜 매개변수와 원래 SQL 기록도 확인했다. 전체 단위 테스트 60개와 wheel 빌드가 통과했다. 실제 모델 호출은 없었다.

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests/unit -p test_semalign.py -v
.venv/Scripts/python.exe -m unittest discover -s tests/unit -p "test_*.py" -v
```
